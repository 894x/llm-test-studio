# Compatibility and data upgrades / 兼容性与数据升级

本项目已经正式公开开源。本政策取代开发阶段“禁止任何兼容代码、只能使用临时脚本转换旧数据”的规则，适用于后续开发和发布。它规定交付要求，不代表现有代码已经实现或验证所有历史升级路径。

## 兼容边界

| 范围 | 要求 |
| --- | --- |
| 已公开的 CLI 命令、参数、退出码、JSON/JSONL 输出和 API | 保持受支持版本的调用方式与语义；删除、改名、类型变化、必填项增加和默认行为变化都需要评估破坏性影响 |
| 桌面端与独立部署的远程 runner | 公布支持的版本组合和升级顺序；不能假设用户同时更新两端，不支持的组合在提交任务或写数据前明确拒绝 |
| 用户配置、Case/Suite/Plan 文件和导入导出格式 | 保持可用，或通过随应用发布且经过验证的转换升级；保留用户内容、身份与引用关系 |
| SQLite、运行快照、历史报告和附件引用 | 提供可恢复的数据迁移；保留历史事实与结论，不能用当前规则重算后冒充原始结果 |
| 内部函数、包结构、同包发布的前后端 binding | 可以同步重构调用方；只有跨越已发布接口或持久化边界时才承担历史兼容要求 |
| 第三方提供商协议 | 在协议边界维护当前支持的适配；与本项目自身数据升级分别验证 |

内部保留一套当前领域模型与业务逻辑。必要的旧字段别名、版本化解码器和协议适配集中在边界，明确来源版本、用途、测试和移除条件；迁移完成后使用当前模型。不要为未发布的开发中间态添加推测性兼容。

## 发布与弃用

- 以实际公开发布的产物和对应提交确定基线，不能用当前开发分支替代历史版本。发布说明必须列出支持的升级来源版本、客户端/runner 组合、已知限制和恢复方式。
- 后续新版本采用 `MAJOR.MINOR.PATCH`，各段不带前导零；已经公开的 tag 和产物不能为了规范命名而重写。版本规则依据 [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html)。
- 在 `0.y.z` 阶段，本项目额外约定：补丁版本保持兼容，必要的破坏性变更安排在次版本，并提供升级说明和经过验证的数据迁移。这是项目约定，不是 SemVer 对 `0.x` 的稳定性保证。
- 从 `1.0.0` 起，同一主版本内保持公开接口兼容；破坏性变更进入下一主版本。数据保全和可恢复升级的要求不会因主版本变化而取消。
- 普通弃用先在一次非预发布版本中公告替代方式及最早移除版本，再在允许破坏性变更的后续版本中移除。安全性问题等紧急例外必须明确说明影响、原因和升级路径。
- 默认保留已公开且未公告终止支持的契约和升级来源。缩短支持范围必须明确发布终止支持说明，并保留可获得的中间升级版本或转换工具；不能在重构时顺带删除仍需使用的迁移步骤。
- 向后升级兼容不等于允许旧程序读取新数据；降级是否需要恢复旧备份必须单独说明。

## 数据迁移必须随代码交付

正常用户升级不应依赖开发者手动改库、删除数据库或运行临时目录中的脚本。持久化格式变更应在同一次修改中交付迁移实现、测试、历史 fixture 与升级说明。

常规打开工作区的顺序应为：

1. 读取并验证数据版本、完整性和支持范围，取得覆盖整个升级过程的排他控制，阻止其他桌面端、CLI 或 runner 同时写入。无法保证排他控制时停止升级。
2. 对需要升级的数据创建一致、可验证、可恢复的备份。SQLite 备份需要正确处理 WAL 等状态，不能仅复制一个可能仍在写入的主文件；不得在日志或测试 fixture 中泄露凭据。
3. 按顺序执行版本化迁移，数据库变更使用事务。文件使用暂存和原子替换；涉及数据库、文件和附件等多个资源时，需要明确检查点、恢复顺序和失败处理。
4. 校验目标结构、记录身份、关联与关键内容，成功后才记录相应迁移完成状态。已发布的迁移编号、内容及校验值保持不可变，新变更追加新步骤。
5. 仅在所需迁移全部完成并校验通过后启动 repository、后台任务与正常业务读写。桌面端、CLI、runner 共用适用的迁移逻辑，避免不同入口绕过检查。

迁移基础设施和受支持的历史迁移长期保留在版本控制与发布产物中。用户跳过若干应用版本时，也应能够通过完整迁移链升级到当前数据模型。应用版本与数据库/文件格式版本分别管理；每次应用发布不一定需要新增数据版本。

已完成的迁移不得重复应用；失败和进程中断后再次启动应安全恢复，或停止并给出可执行的恢复说明。未知、损坏、超出支持范围或来自更高版本的数据在任何迁移写入之前拒绝，保留原数据。历史无版本标记的数据只有在已发布来源和识别规则明确、无歧义并经过测试时才允许转换，不能把任意缺失版本都当成某个旧版本。

旧数据库升级与旧报告导入是不同入口：导入受支持历史文件时，先在内存或暂存区转换并验证，再写入当前格式；默认不改写用户提供的原始文件。历史报告保留原始执行结果、时间、来源和证据，不得填造过去未采集的数据。

降级默认不能通过直接启动旧二进制实现。恢复旧备份需要对应版本的程序，且可能丢失升级后新增记录；发布说明必须写明限制。特殊损坏修复或超出常规支持范围的转换可以使用独立工具，但不能替代正常升级的代码路径。

## 验收要求

- 从每个受支持且具有不同存储格式的发布版本准备脱敏 fixture，覆盖实际发布格式，不能仅用当前模型生成“旧数据”。
- 验证全新初始化、逐步升级、跨版本升级、升级后重复打开和正常读写。
- 验证迁移失败、进程中断、磁盘/权限错误、并发打开、备份失败及恢复；涉及多资源时验证部分完成的恢复。
- 核对记录数量、身份、关联、用户自定义内容、凭据引用和历史报告语义；保持原始历史证据。
- 验证未知/较新/损坏格式被明确拒绝，拒绝前后原数据未被修改。
- 验证备份可恢复到匹配版本的可用工作区。数据库事务回滚不等于整次升级、文件变更和应用降级均已验证。
- 在 PR 和发布说明中区分：政策已更新、迁移代码已实现、fixture 已通过、实际用户数据已升级。没有实际执行证据，不得宣称最后一项完成。

目标为 `user_version=3 / 0003_query_indexes`。原有 `0002_operational_upgrades` 的结构与校验和冻结，来源为上述 10 个 v1 结构以及已发布的 v2。v1 按 1→2→3 顺序升级；v2 仅追加查询索引和第 3 条迁移记录，全部业务表行值及前两条账本原样保留。索引覆盖运行、报告、对比的时间排序、快速测试修订筛选和任务事件的类型/序号定位，不重算历史结论。空库直接建立当前结构及完整账本。新变更必须追加迁移，不得修改已冻结的来源定义来接受不认识的库。

### 数据保留与执行边界

- 全部来源表的行值、SQL 类型和自增高水位在迁移前后校验；运行、修订、证据、结果、报告、附件引用和旧统计表保留。新增表不会覆盖旧数据。
- `8613f4bd` 以前的报告增加 `execution_origin: null`，其余报告字段、采样、结论和历史时间保留；原始字节保存在迁移前备份中。不能拿准备机器的信息填造实际执行来源。
- 这 7 个起点的旧 Job 缺少当前必需的执行器版本、OS、架构等信息。原始 Job、事件、控制指令、提交、远程镜像及性能结果按 SQL 类型和原始字节存入 `upgrade_history_*`，保留 Job/Run 归属和报告 ID。它们是只读历史档案，不再作为当前队列恢复、重发或继续执行；原始 queued/running/completed 状态不改写。需要再次执行时创建新 Job。
- 已存的 Run/Report 仍可通过当前历史读取接口读取；归档 Job 和独立性能结果通过下述导出命令查看，暂不混入当前任务列表。新任务仍必须提供完整执行来源，内部任务模型和远程协议未放宽。
- 控制目标迁移只从持久化提交意图及原始接受凭据确定，禁止按当前 UI 选中的节点推断。

### 自动升级、备份和恢复

桌面端与 runner 在获取各自实例锁后、打开业务 repository 前调用共享 `Migrate`。SQLite `BEGIN IMMEDIATE` 阻止迁移期间的其他写入；备份通过独立只读快照及 SQLite online backup 读取已提交 WAL，核对表结构、完整性和逐表内容后持久化，随后才修改业务数据。全部数据库变更在同一事务提交；失败回滚，保留备份。已经升级的库重复打开不重做迁移、不再建立备份。

备份位于数据库旁的 `<database>.upgrade-backup-*/database.sqlite`；Windows 验证完成的目录名以 `-verified` 结尾。备份包含原始用户数据，应和工作区采用相同的访问保护。未通过验证的残留目录不是可用备份，不能自动恢复。

恢复时先退出全部使用该数据库的桌面端和 runner，保留当前数据库及其 WAL/SHM 副本，在一个新位置复制经过验证的原版本备份，使用对应旧版本验证后再替换工作区。不要将备份主文件与当前库遗留的 WAL/SHM 混用。升级后新增数据不在旧备份中；不能直接使用旧程序打开 version 3 数据库。v2→v3 同样先生成包含 WAL 的 v2 备份，恢复该备份后才能使用匹配的 v2 程序；升级后新增记录不会出现在旧备份中。

### 导出只读历史档案

```sh
llm-test-studio data export-upgrade-history --database /path/workspace.db --output /path/new-history.jsonl
```

命令只读打开已经升级的库，不会迁移来源，不覆盖已有输出。输出含来源校验和、列名、行数、逐表 SHA-256 及逐行原始 SQL 单元格；`blob` 为 Base64，`integer` 为十进制字符串，`real` 为 IEEE-754 位模式的十六进制字符串，保留数值精度。最后必须有 `type: complete` 记录；中断后的不完整文件不能当作完整导出。导出包含原始工作区内容，不会打印到终端日志。

### 测试与尚未覆盖的边界

测试 fixture 从上述每个提交的实际 Go 写入器生成，覆盖运行、修订、结果、证据、报告、附件引用、快速性能报告、本地 Job，以及该版本已有的远程 Job、提交和控制指令。另有执行真实本地测试服务产生的旧性能观测和封存结果 fixture，以及从 `e72dc1fc` 原始代码生成的 v2 结构和数据 fixture；后者验证索引升级、逐表内容保留、失败回滚、重复打开和备份恢复。文件位于 `internal/persistence/sqlite/testdata/migrations/`，不能用当前结构伪造替代。

自动化测试覆盖跨版本升级、重复打开、迁移前备份再次升级、WAL 数据、并发升级、占用写锁、取消、坏文档回滚、原始 Job/性能结果保留、恢复队列隔离、历史 ID 保护、当前协议来源校验和只读导出。测试数据库均在临时目录；没有迁移实际用户数据库。

本轮窗口不包括更早的 `v0.0.01` schema 7、之前的 authored/operational 布局、旧默认配置目录迁移，也不承诺历史客户端与当前 runner 的协议组合兼容。未知、较新、被篡改或窗口外的数据库明确拒绝且不重置数据。配置文件、凭据存储、附件实际文件内容和第三方协议未发生本轮格式转换。完整工作区恢复、原生桌面安装包升级、真实磁盘断电及磁盘满场景仍需发布验收；数据库 fixture 测试不代替这些验收。

既有历史设计和验收记录保留当时事实，不改写成“已兼容”。
