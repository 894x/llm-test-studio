# Compatibility and data upgrades / 兼容性与数据升级

## v0.2.1 发布决定与升级顺序

`v0.2.1` 基于已公开的 `v0.2.0`，交付以下具备显式能力门禁的增量扩展。
此前开发记录中的“下一次 minor”安排由本次版本决定取代；保留受支持的旧输入、
目录引用和历史数据，不将 patch 版本号视为旧严格解码器可读取新字段的承诺。
新步骤、断言失败策略和 HTTP 头证据会进入 Case、冻结任务及其快照／报告／归档。

创建新任务前，等待现有任务结束，保存编辑并备份完整工作区和匹配旧程序；
先更新所有需要观察新任务的桌面客户端及所用 runner，再启用新功能。
`sequence_steps` 和 `assertion_failure_status` 必须由执行器声明；
`http_header_evidence` 按能力协商，未支持时保持缺省行为。桌面内更新不更新 runner。
本次没有新增 SQLite 结构或迁移步骤，既有升级来源、旧格式支持窗口及拒绝规则保持。

降级需恢复启用这些新字段前的工作区备份和匹配程序，恢复点之后的写入不在其中。
六个退出可选目录的旧缓存 Suite 继续按原 ID 只读解析，适配暂无移除日期；
用户覆盖、冻结快照与历史结论不因常规升级自动重写。新增功能和实际验证范围见
[v0.2.1 发布说明](releases/v0.2.1.md)。下文保留各功能演进记录，最终行为以较前的补充说明为准。

## 断言证据不足与 HTTP 头证据（v0.2.1）

本次升级基线为 `v0.2.0`。Case 仍读取支持的 schema 2/3；现有断言默认行为和编码
不变，新增可选 `failure_status` 只接受 `indeterminate`。未设置时失败仍是 failed，
不能把失败改成 passed。新策略的任务必须通过 `assertion_failure_status` 能力门禁，
不支持的执行器在提交前明确拒绝，不能静默按旧语义执行。旧文件继续工作，不新增
历史版本猜测或弃用日期。此节覆盖下文此前“仅改断言、不增加 runner 能力”的范围。

功能及对比任务在执行器支持时冻结可选 `http_header_evidence: true`；未支持时保持
缺省标记和原有结果格式。旧任务交给新执行器仍不新增头字段。启用后 Exchange
增加可选的已脱敏 `request_headers/response_headers`，各含 `values` 和可选截断标记。
未记录不补空头，不把数值指标冒充 HTTP 头。数据库结构、user_version、迁移账本、
公开 CLI 选项和退出码不变。新结果可在现有 JSON/SSE、持久化和归档路径往返。

Case 分项使用已有断言组和 Verdict 枚举；报告详情可选 `verification_checks` 是 Go
按记录组结果提供的读取投影，不在 React 重算业务结论。没有分组的旧报告保持旧
展示和结论；头字段缺省的历史继续读取。当前明确授权的七渠道对比单独重评，
结果规则标记为 `kimi_cache_checks_20261112`，保留原始执行输入与全部观测，其他历史
不自动迁移。先在线备份、隔离副本验证，再按条件单事务更新结果和 journal 摘要。

旧严格客户端不认识新 Case 策略和启用字段。创建新功能任务前应更新需要读取它的
桌面端及使用的 runner；旧客户端提交的旧任务仍保持原编码。回退需要更新前的
完整工作区备份及匹配二进制，备份后的新增写入不在恢复范围，不能用旧规则重算
本次结果。没有增加 DB 升级来源窗口或要求用户删除数据库。

## Kimi TTL 双响应形式与授权的定向重评

综合对账和延迟验证保留 schema、身份、引用、请求和等待，只更新内置断言。
三协议 JSON/SSE 接受 header 或 usage 的可核对 TTL 分项，所有已返回字段仍须
一致；Chat/Responses 的零字段省略规则见 [缓存说明](kimi-cache-usage.md)。没有
新增历史格式分支、数据库结构或 runner 能力，目录覆盖优先级不变，无格式弃用。

通常仍不追溯改变既有报告。本次用户明确指定替换当前 Kimi 对比结论，作为限定
任务 ID 的一次性修复：在线一致备份、隔离副本演练、原始证据摘要核对、单事务
条件更新及完整仓储/报告读回。原执行输入和冻结快照保留为实际发送记录，重评
请求结果并重建 Case/Suite/报告及 journal 摘要；结果 Dimensions 标记
`verification_rules=kimi_ttl_dual_20261112`。它使用现有字符串字典，Entry marker
不增加字段；其他历史和在途任务不自动迁移。

这不是常规升级迁移，不要求其他用户删除或修复数据库。失败事务不保留部分
结论，完整修复前备份是恢复点。撤销本次修复需恢复该备份及匹配程序，备份后的
新增写入不在恢复点中。旧二进制可读同格式结果，但其内置规则仍旧，不能用来
声称复现本次新规则的评估；没有改变原有数据格式支持窗口或增加移除计划。

## 报告读取去重（v0.2.1，2026-11-12）

功能及计划性能报告的读取在同一只读事务中复用已校验的运行快照和证据，
保留请求结果、执行标记、附件、封存状态和归属的完整性检查。运行修订只完整
解码一次冻结快照，后续修订仍通过当前领域状态机验证转换，并将完整规范化
文档逐字节比对；未知字段、变化的快照及非规范编码仍拒绝。功能和独立性能
报告的应用服务不再重复执行存储边界已经完成的全文校验。

这是同包应用与仓库之间的内部读取端口调整，不改变 v0.2.0 及当前支持来源
的报告、快照、导出 JSON、CLI、桌面或 runner 协议与数据库格式，不改写历史
结论或用户数据，无迁移、弃用、适配器移除期限或额外降级转换。原有支持窗口
和降级限制保持。验证涵盖报告与导出回归、损坏输入拒绝、重复读取及调用方
修改隔离；当前用户库只用于只读计时，未进行原生客户端重启验收。

## 发布与弃用

- 以实际公开发布的产物和对应提交确定基线，不能用当前开发分支替代历史版本。发布说明必须列出支持的升级来源版本、客户端/runner 组合、已知限制和恢复方式。
- 后续新版本采用 `MAJOR.MINOR.PATCH`，各段不带前导零；已经公开的 tag 和产物不能为了规范命名而重写。版本规则依据 [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html)。
- 在 `0.y.z` 阶段，本项目额外约定：补丁版本保持兼容，必要的破坏性变更安排在次版本，并提供升级说明和经过验证的数据迁移。这是项目约定，不是 SemVer 对 `0.x` 的稳定性保证。
- 从 `1.0.0` 起，同一主版本内保持公开接口兼容；破坏性变更进入下一主版本。数据保全和可恢复升级的要求不会因主版本变化而取消。
- 普通弃用先在一次非预发布版本中公告替代方式及最早移除版本，再在允许破坏性变更的后续版本中移除。安全性问题等紧急例外必须明确说明影响、原因和升级路径。
- 默认保留已公开且未公告终止支持的契约和升级来源。缩短支持范围必须明确发布终止支持说明，并保留可获得的中间升级版本或转换工具；不能在重构时顺带删除仍需使用的迁移步骤。
- 向后升级兼容不等于允许旧程序读取新数据；降级是否需要恢复旧备份必须单独说明。

## 数据迁移必须随代码交付

正常用户升级不应依赖开发者手动改库、删除数据库或运行临时目录中的脚本。持久化格式变更应在同一次修改中交付迁移实现、测试、历史 fixture 与升级说明。

常规打开工作区的顺序应为：

1. 读取并验证数据版本、完整性和支持范围，取得覆盖整个升级过程的排他控制，阻止其他桌面端、CLI 或 runner 同时写入。无法保证排他控制时停止升级。
2. 对需要升级的数据创建一致、可验证、可恢复的备份。SQLite 备份需要正确处理 WAL 等状态，不能仅复制一个可能仍在写入的主文件；不得在日志或测试 fixture 中泄露凭据。
3. 按顺序执行版本化迁移，数据库变更使用事务。文件使用暂存和原子替换；涉及数据库、文件和附件等多个资源时，需要明确检查点、恢复顺序和失败处理。
4. 校验目标结构、记录身份、关联与关键内容，成功后才记录相应迁移完成状态。已发布的迁移编号、内容及校验值保持不可变，新变更追加新步骤。
5. 仅在所需迁移全部完成并校验通过后启动 repository、后台任务与正常业务读写。桌面端、CLI、runner 共用适用的迁移逻辑，避免不同入口绕过检查。

迁移基础设施和受支持的历史迁移长期保留在版本控制与发布产物中。用户跳过若干应用版本时，也应能够通过完整迁移链升级到当前数据模型。应用版本与数据库/文件格式版本分别管理；每次应用发布不一定需要新增数据版本。

已完成的迁移不得重复应用；失败和进程中断后再次启动应安全恢复，或停止并给出可执行的恢复说明。未知、损坏、超出支持范围或来自更高版本的数据在任何迁移写入之前拒绝，保留原数据。历史无版本标记的数据只有在已发布来源和识别规则明确、无歧义并经过测试时才允许转换，不能把任意缺失版本都当成某个旧版本。

旧数据库升级与旧报告导入是不同入口：导入受支持历史文件时，先在内存或暂存区转换并验证，再写入当前格式；默认不改写用户提供的原始文件。历史报告保留原始执行结果、时间、来源和证据，不得填造过去未采集的数据。

降级默认不能通过直接启动旧二进制实现。恢复旧备份需要对应版本的程序，且可能丢失升级后新增记录；发布说明必须写明限制。特殊损坏修复或超出常规支持范围的转换可以使用独立工具，但不能替代正常升级的代码路径。

- v1 的数据转换在迁移前后校验来源表的行值、SQL 类型和自增高水位；运行、修订、证据、结果、报告、附件引用和旧统计表保留。v2/v3 后续仅增加索引和空表，不改写历史行；自动化回归仍逐值验证这些来源的数据保留与备份恢复。
- `8613f4bd` 以前的报告增加 `execution_origin: null`，其余报告字段、采样、结论和历史时间保留；原始字节保存在迁移前备份中。不能拿准备机器的信息填造实际执行来源。
- 这 7 个起点的旧 Job 缺少当前必需的执行器版本、OS、架构等信息。原始 Job、事件、控制指令、提交、远程镜像及性能结果按 SQL 类型和原始字节存入 `upgrade_history_*`，保留 Job/Run 归属和报告 ID。它们是只读历史档案，不再作为当前队列恢复、重发或继续执行；原始 queued/running/completed 状态不改写。需要再次执行时创建新 Job。

- 控制目标迁移只从持久化提交意图及原始接受凭据确定，禁止按当前 UI 选中的节点推断。

### 自动升级、备份和恢复

桌面端在数据结构不受支持，或已明确识别的历史报告、控制记录等内容无法安全迁移时，提供需用户确认的“备份并创建新数据库”。应用保留原库和附属文件，创建并校验一致性备份；对于结构仍受支持的历史库，还会在临时副本上重试迁移，确认不兼容仍存在，再切换到空白库并重新初始化工作区。临时副本及迁移探测需要额外磁盘空间和时间。旧历史、任务和数据库配置不会自动进入新库，原数据仍需另行修复或使用匹配版本访问。磁盘、权限、锁、物理损坏或原因尚未确定的迁移失败不会仅凭失败阶段被当成内容不兼容；备份验证失败时不会切换，切换结果无法确认时提示重启检查且不允许重复创建。此功能不改变数据库格式或受支持升级来源，也不替代正常迁移；旧版本仍不能直接读取新格式，降级需要恢复匹配版本的备份，备份后的写入不会保留。

桌面端与 runner 在获取各自实例锁后、打开业务 repository 前调用共享 `Migrate`。SQLite `BEGIN IMMEDIATE` 阻止迁移期间的其他写入；备份通过独立只读快照及 SQLite online backup 读取已提交 WAL，检查复制结果、原版本结构、外键和 SQLite 完整性，执行持久化同步及文件身份检查后才发布可恢复备份。备份不再对源库和副本额外逐表排序、计算业务摘要。全部数据库变更在同一事务提交；失败回滚，保留备份。已经升级的库重复打开不重做迁移、不再建立备份。

v2→3→4 和 v3→4 的纯新增结构升级只验证来源备份及目标结构，不重复遍历、解码未修改的历史业务 JSON，也不重新判定历史结论。既有文档仍由对应读取/导入边界校验；这不代表对全部历史业务文档进行了语义审计。确实转换旧数据的 v1 升级保留内容摘要及转换后的文档/关联验证。迁移版本、冻结结构、校验和、支持的来源、备份恢复及降级限制不变。

2026-10-30 本机单次基准：32 MiB 数据的 v2→4 为 0.94 秒、v3→4 为 0.84 秒；1,165,152,256 字节的真实 v3 备份副本升级为 15.54 秒，其中备份及完整性检查 15.43 秒。计时包含完整 `Migrate`，不包含测试副本准备和计时外的全量内容比对；升级库与生成备份的来源表值、类型、自增高水位均比对通过。这是本机热缓存样本，不是磁盘性能或耗时 SLA。

可用 `go test ./internal/persistence/sqlite -run '^$' -bench '^BenchmarkAdditiveMigration$' -benchtime=1x` 复测；可选环境变量 `LLM_TEST_MIGRATION_BENCH_SOURCE` 指向独立、一致的 v2/v3 备份。基准只迁移临时副本，不接受带未提交 WAL 的源文件。既有回归继续覆盖 10 种 v1 格式、v2/v3、备份恢复、重复打开、未知/较新结构拒绝、取消回滚、WAL 和并发写入；新增用例验证外键损坏的 v2/v3 在修改前拒绝。

备份位于数据库旁的 `<database>.upgrade-backup-*/database.sqlite`；Windows 验证完成的目录名以 `-verified` 结尾。备份包含原始用户数据，应和工作区采用相同的访问保护。未通过验证的残留目录不是可用备份，不能自动恢复。

恢复时先退出全部使用该数据库的桌面端和 runner，保留当前数据库及其 WAL/SHM 副本，在一个新位置复制经过验证的原版本备份，使用对应旧版本验证后再替换工作区。不要将备份主文件与当前库遗留的 WAL/SHM 混用。升级后新增数据不在旧备份中；不能直接使用旧程序打开它不支持的 version 3 或 version 4 数据库。v2 和 v3 来源均先生成包含 WAL 的对应版本备份；降级时恢复该备份并使用匹配程序，备份之后的记录和回收站操作不会保留。

### 耗时 SLA 的两位小数比较

新执行的功能测试对耗时 SLA（`ms` 和 `ms/token`）先聚合原始观测，再将观测值和阈值分别按十进制四舍五入保留两位小数后比较。边界相等达标，例如阈值为 `50 ms` 时，`50.004 ms` 达标，`50.005 ms` 超标。`0 ms` 是正常观测，按同样规则比较；缺少样本仍按原规则处理。速率、计数 SLA 的比较规则不变；性能测试 SLO 按下节采用同样的耗时精度。计时来源、原始指标、用户填写的阈值均保留，不提前舍入采样。

该语义通过现有结果 `dimensions.sla_precision=latency_2dp_v1` 标记，适用于本地和 runner 的新功能请求结果，以及执行中的失败策略和报告生成。所有参与比较的测量结果均带此标记时才启用新规则；无标记的历史结果和混合来源结果保持原始精度比较，包括尚未生成报告的旧运行。已有报告直接保留。未知的标记值明确拒绝，不能猜测其语义。

这是现有 JSON 扩展字段中的版本化语义，不修改 SQLite 结构、迁移账本、快照或报告版本，也不改写历史行；支持窗口仍为上文列出的数据库来源。无标记兼容路径在这些历史结果仍受支持期间保留，暂无移除日期。旧客户端可以读取既有结果维度，但旧二进制不理解新精度语义，不支持用其重新生成新运行的报告；需要回退时使用更新前的工作区备份及匹配二进制，备份之后的写入不会保留。

回归样本 `internal/application/reporting/testdata/legacy-sla-precision-c561055d.json` 由 `c561055d` 的实际报告生成器生成，保存 `1000.004 ms > 1000 ms` 的旧失败结论。测试验证旧报告读取与延迟生成的规范化 JSON 一致、原始值保留、未知标记拒绝，并通过真实本地 HTTP → 执行器 → SQLite → 报告及远程报告编码覆盖新规则的零值、舍入边界和继续/停止策略。没有修改或迁移实际用户数据库。


### 性能 SLO 与功能 SLA 统一耗时精度

快速性能测试、计划中的性能项、本地及远程 runner、容量阶梯的 TTFT / TPOT / E2E 达标判定共用功能 SLA 的两位小数舍入实现。SLO 对每个请求的原始耗时与阈值分别舍入后比较，再计算达标率和 goodput；功能 SLA 仍先聚合再比较，不把两种统计粒度混淆。相等达标；原始指标、阈值和达标率保留原始精度，SLO 目标百分比也不舍入。阈值原始值为 0 仍表示未启用，正数阈值即使舍入到 0.00 也保持启用。超时、调度、截止时间和数据完整性校验不使用两位小数容差。

新 `slo_assessment.latency_precision=latency_2dp_v1` 标记比较规则，同一容量运行的各档位使用相同规则。没有该字段的历史报告继续使用精确比较和原来的零值判定；未知值明确拒绝。真实流式语义事件通过可选 `ttft_observed` 标记区分零 TTFT 与未取得首 token，已观测的零 TTFT / TPOT 不再被丢出统计分布。TPOT 仍要求取得首 token 且输出 token 数大于 1；缺少观测仍算违规，传输失败仍计为失败。成功请求的 E2E 0 ms 正常参与判定。这些扩展字段省略零值，不会给旧记录补字段或重写历史结论。

SQLite 结构、`user_version` 和既有迁移链不变，支持的历史数据窗口沿用上文。当前 schema 2 的无标记性能报告可直接读取、校验和传输，不需要数据迁移；兼容逻辑在支持这些报告期间保留，暂无移除日期。旧桌面端及 runner 使用严格字段解码，不能消费带新标记的报告，因此本次作为需要**桌面端与全部 runner 同步更新**的协议扩展发布，不支持新旧版本混用。更新前停止并等待在途任务结束，备份工作区后更新各端，再创建新任务。若必须降级，恢复更新前备份并使用匹配版本；之后新增记录不在旧备份内，不能用旧版本重算新报告。

`internal/application/quicktest/testdata/legacy-slo-*-220a2185.json` 来自 `220a2185` 的真实报告生成和校验代码，覆盖阈值附近旧失败及旧零值失败。新报告 fixture 与 Go 生产构造的输出逐字段校验，并供前端解析、SQLite 往返、远程归档编码及混合计划嵌套报告解码共用。回归测试覆盖两端阈值舍入、零值与缺失值、容量选择/停止、统计与时间切片、检查点、未知标记拒绝及失败写入不修改原记录。

## 快速性能测试的会话亲和开关

性能配置增加可选布尔字段 `affinity_enabled`，默认关闭。旧性能计划、schema 2 报告、任务输入及已拷贝的完整参数 JSON 缺少此字段时保持关闭；前端参数导入拒绝非布尔值。关闭时 Go 序列化省略该字段，保留旧配置的编码与摘要。SQLite 结构、版本和既有迁移链不变，不重写历史数据，不改变历史报告结论。支持的数据来源沿用本文已有窗口；该缺省规则在历史配置仍受支持期间保留，暂无移除日期。

启用后，每次实际执行生成新的随机会话标识，同一测试的预热、爬坡、容量阶梯和正式请求复用该标识。OpenAI Chat/Responses 发送 `prompt_cache_key`，Anthropic Messages 发送 `metadata.user_id`。该设置随性能计划保存、参数拷贝、任务冻结和报告传递。它仅向网关提供亲和键，实际渠道选择、故障切换和缓存命中由网关／上游决定；网关需要配置匹配模型、路径和字段的亲和规则。关闭表示不主动发送亲和键，不会覆盖网关其他既有路由策略。

启用的任务要求 runner 声明 `performance_affinity` 能力，缺少能力时在投递前拒绝，不允许静默忽略开关。发布使用本功能前应同步更新桌面端与使用的 runner；旧桌面端／runner 的严格解码器不能读取包含启用字段的新配置或报告。未启用时不新增 runner 能力要求。没有更改公开 CLI 选项或退出码，也没有弃用既有字段。

降级需要恢复使用此功能前的工作区备份及匹配二进制；之后写入的启用配置和报告不能直接交给旧版本，恢复旧备份不包含后续写入。回归测试覆盖三种协议的实际本地 HTTP 请求、固定／随机／正态负载、预热／爬坡／容量阶段、跨执行键隔离、报告校验、计划与 SQLite 往返、旧参数导入、类型拒绝和 runner 能力检查。实际网关渠道命中与原生安装升级需要另行验收。

## 远程报告的协商压缩下载

桌面端首次完整下载运行报告、性能结果及性能归档时，通过既有 `Accept-Encoding: gzip` 协商压缩传输；runner 仅在报告至少 64 KiB、客户端明确接受 gzip 且请求不含 `Range` 时压缩响应，小报告继续避免压缩开销。压缩只改变线上表示，报告引用的大小和 SHA-256 始终对应解压后的原始 JSON，缓存、导入和历史报告结论不变。客户端仍接受 identity 响应，因此新桌面端可读取未实现压缩的旧 runner；旧桌面端不声明 gzip，也可继续读取新 runner。协议版本、公开 CLI、数据库结构和既有迁移链不变，不要求桌面端与 runner 同步升级。

带 `Range` 的断点续传继续使用 identity、原始字节偏移及 `Content-Range`，压缩响应不能用于续传。客户端限制压缩线上字节数和解压后报告大小，并校验 gzip CRC、单成员 framing、尾随数据及最终原始摘要。回归测试覆盖首次下载的线字节数、旧 runner identity 回退、Range 续传、损坏／截断／多成员／额外 decoded 数据拒绝及原始报告逐字节一致性。该协商能力在支持的远程协议版本期间保留，暂无移除日期。

## 快速功能测试的在途数量

新快速功能任务在执行器声明 `functional_progress` 能力时，冻结可选任务字段 `functional_progress: true`，通过现有 `progress` 事件上报请求调度器的实际在途数量。本机和远程 runner 使用相同实现；只计已开始而尚未结束的 Case 执行，不将排队任务、剩余预算或配置并发数当成在途。界面的通过、失败仍取持久化的功能结论，不使用调度器的传输成功数替代断言结果。结束和取消时刷新最终进度，历史结论与报告内容不变。

缺少标记的既有任务保持原有编码、摘要和行为，新 runner 不为其新增功能进度。新桌面端连接未声明能力的旧 runner 时仍可提交原有任务，但在途数量保持未知。新进度只用于显式标记的单个快速功能 Run，不用于对比任务或普通计划，不修改公开 CLI、数据库结构、迁移版本或历史数据，也没有移除旧标记缺省路径的计划。

旧桌面端的严格解码器不认识启用标记的新任务。使用共享 runner 时，先更新所有需要观察这些新任务的桌面客户端，再创建启用任务；新版桌面端可以继续观察无标记的旧任务。需要回退到不支持该标记的二进制时，使用启用功能前的工作区备份及匹配程序，备份后的新增任务不在恢复范围内。该变更不声称覆盖旧公开标签 `v0.0.01` 的 schema 7 数据升级，数据库支持窗口沿用本文已有政策。

本次进行 Go 编译、前端类型检查、lint、构建和固定数据的浏览器呈现检查；未运行自动化测试或真实付费供应商请求，未验收旧版本原生客户端与新版 runner 的混合运行。

桌面报告详情新增可选 `performance_overviews` 读取投影，键为独立性能报告 ID 或计划中的性能项 ID；仅随桌面前后端一起发布。没有投影的既有详情和 JSON 导出继续按原有摘要展示，不猜测目标或在前端补算结论。性能报告正文、快照、SQLite 结构、迁移链、runner 协议、CLI 及 JSON 导出的字段和编码不变，不重写历史数据，也不增加降级所需的数据转换。

概览的请求成功率沿用既有全部请求成功标准，SLO 达标率保留封存状态。TTFT / TPOT / E2E P95 对照封存的逐请求 SLO 上限，作为明确标识的参考比较，采用该报告原有的精度语义；这是读取时的辅助展示，不是追溯新增考核目标，也不替代历史传输、逐请求 SLO 或容量结论。未配置的指标仅观测，缺少观测保留空值，中断或未评估的执行不产生通过结论。达标项数只计实际完成对照的指标，观测和未评估项另列。

HTML 与桌面图片、PDF、复制图片展示相同的核心概览；HTML 原有 TPOT / E2E 分位数信息继续保留在时延分布中。没有弃用或删除历史字段，也没有适配器移除期限。回归覆盖精度边界、零值与缺失值、停止执行、旧详情缺省、JSON 导出不变和概览不修改封存报告；原生安装包升级及真实供应商负载需另行验收。

## 用例说明的版本化保存

新增说明安排在下一次次版本发布。Case 文件继续读取 schema 2；无说明保存为 schema 2，原有摘要与派生修订保持。非空说明保存为 schema 3；v2 出现说明字段、v3 缺少有效说明及未知字段或版本明确拒绝，不修改来源。v2 支持路径暂无移除计划。

说明与定义一起冻结在新运行快照中，目录修改不改写历史运行和报告。带说明的远程任务要求 runner 声明 case_descriptions，缺少能力在提交前拒绝；无说明任务不增加此能力要求。查看新任务的共享桌面客户端应先更新；旧严格解码器不能读取新增字段。Case/Suite/Plan 身份、引用、CLI 机器输出和退出码保留。

需要降级时恢复使用说明前的 Case 文件、工作区备份及匹配程序；旧程序不能直接读取 schema 3 Case 或带说明的新快照，备份后的写入不在恢复范围。回归测试覆盖旧 v2 摘要与修订、保存与清空、拒绝无效替换不修改文件、远程能力门禁及历史快照冻结。

## v0.1.5 计划测试与临时连接

桌面计划启动参数新增可选 `connection`，与既有 `model_id` / `channel_id` 选择互斥；未提供时沿用原有启动方式，没有弃用或移除日期。该输入由同包桌面前后端共同更新，在桌面准备阶段消费，不扩展 runner 任务协议。三种测试模式支持渠道填充或临时地址、模型 ID、协议和 API Key，候选计划按协议筛选。

复用现有计划准备与执行：保留计划身份、全部执行项及失败策略，只冻结本次连接；临时密钥通过独立租约交付，不写入计划、快照、提交队列或日志。只有显式保存连接才创建目录配置。计划文件、数据库结构、快照 schema、报告及导出 JSON 没有新增格式，不需要数据迁移，也不改写历史结论。此次变更不扩大旧 schema 7 数据的升级支持窗口。

历史记录与正式报告沿用当前读取边界。再次执行使用当前保存的计划版本；跨会话的临时连接历史需重新填写地址和密钥。Go 回归覆盖原有启动方式、临时连接、保存渠道、完整多执行项冻结、冲突拒绝与密钥隔离；前端覆盖内置十档和自建计划、协议筛选、独立任务、控制、历史回填、目录状态及连接草稿保留。
