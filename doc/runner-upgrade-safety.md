# Runner 升级与失败恢复（2026-11-05）

远程 Runner 的程序版本、数据库版本和升级操作阶段分别核验。`backing_up`
表示最后到达的阶段；该记录同时有 `error_code` 时，不代表备份还在执行。
连接失败也不能用来推断远端升级已经停止。

## 本次修复与兼容范围

- 升级专用备份接受正式迁移目录中的十个 version 1 基线，以及 version 2、3、4。
  基线必须同时匹配迁移记录、校验和和实际数据库结构，不能仅凭 `user_version=1`
  猜测布局。未知、较新、损坏和不兼容业务内容拒绝升级，不重置数据。
- 保持原有 `BackupRunnerDatabase` / `VerifyRunnerDatabase` 的当前版本校验契约。
  升级使用独立入口；旧库备份保留原 schema、原始类型值、迁移记录和已提交 WAL。
  不用当前业务解码器重新解释旧报告，也不重算历史测试结论。
- 暂停任务接入或停止服务前，先在私有一次性副本中运行随应用发布的同一套 `Migrate`，
  再验证目标库。预检失败时，旧 Runner 继续提供服务。预演副本不替换源库或正式备份。
- 正式备份仍在升级排他控制下生成并验证；历史格式的正式备份也在独立副本上预演迁移，
  防止初次预检之后出现的不可迁移数据被忽略。切换到新程序后，由共同的正式迁移入口
  在正常 repository 和后台写入启动前升级数据库。
- 不增加或删除公开 CLI 命令、选项、远端升级阶段或 journal 字段；已保存的升级记录、
  原恢复权限与恢复接入后的禁止还原规则继续生效。没有新增弃用或移除期限。
- 桌面出现升级错误或状态读取错误时，显示“升级需要处理”和上次阶段，停止阶段转圈，
  保留原操作、错误、读取状态、重试和允许的恢复入口，不再宣称后台仍在执行。
- “同时运行任务数”移至节点编辑页，节点列表不再直接展示输入框。该设置通过既有
  命令独立保存，不提交或清空尚未保存的连接配置；1–128 的范围及运行中任务保护不变。

version 1 的正式迁移已经在提交前完成目标库深层校验，预检不再重复同一轮全库检查；
version 2、3 的新增结构迁移仍保留额外业务校验。结果校验沿既有
`(run_id, created_at, id)` 索引进行键集分页，包含时间相同的记录，不新增索引或修改 schema。

## 发布与操作顺序

1. 发布包固定源提交、源是否有未提交修改、程序 SHA-256 和版本，桌面与对应 Runner
   使用匹配发布包。保留旧发布包及其 manifest，不覆盖原版本或手工替换缓存文件。
2. 在支持的真实历史 fixture 上验证跳版本迁移、WAL、备份还原、重复打开、取消、
   中断恢复及未知格式的无修改拒绝；发布说明明确支持窗口。
3. 升级前确认没有未完成任务，核对服务器身份、当前构建和操作编号，并保留足够空间
   容纳源库、正式备份和迁移预演副本。预演成功不等于已经升级线上数据库。
4. 预检及备份验证通过后才继续切换；失败保留错误和原操作编号，不自动新建操作，
   不通过删库、改版本号或修改历史 checksum 绕过拒绝。
5. 失败后先读取已保存的阶段及错误。仍选择旧构建、未获得恢复备份权限且未尝试恢复
   接入时，停止后的失败路径可以重新启动并验证旧服务；维护接入仍保留关闭。
   通过“恢复升级前状态”显式恢复接单并确认 `ready/healthy`，再处理失败原因。
   这保留同一操作的重试能力，避免在未确认安全时自动开放接入。
6. 原升级包不支持旧库时，先完成原操作的恢复，再从包含本修复的新发布包发起新操作。
   不能在旧操作中替换目标 SHA-256；反复重试相同旧包不会补上缺失的迁移支持。

## 数据与降级

升级备份包含一致快照及原 schema 身份。受支持的迁移遵循
[兼容性与数据升级政策](compatibility-policy.md)，不删除用户记录、报告或凭据引用。
恢复旧版本必须使用对应旧程序和匹配的升级前备份；不要混用备份主文件与当前 WAL。
恢复任务接入后可能已经产生新写入，不再允许把旧数据库还原覆盖当前数据。
旧备份不包含备份之后的新写入，不能将“能升级”理解为旧程序可以读取新数据库。

本次短剧服务器恢复使用既有的 `recover-upgrade` 操作，只恢复原程序的服务及接入，
没有把线上数据库迁移到新版本，也没有执行新版本上线。恢复前的一致快照与原始
数据库/WAL、配置及凭据另存于服务器私有备份目录；本机验收回执不包含凭据。
