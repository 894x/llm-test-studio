# 桌面启动失败与恢复提示

启动失败由 Go 初始化层按已有错误身份和 SQLite 主错误码分类，前端只接收
`GetStartupProgress.failure_code` 的固定枚举并显示中英文原因、恢复步骤、停止阶段和日志入口。
未知错误不推断为历史数据不兼容；原始错误链继续交给已有 startup 日志记录器，
不将路径、凭据或原始异常传入页面。

| 错误标识 | 恢复方向 |
| --- | --- |
| `workspace_busy` | 在原实例完成或停止任务并退出，关闭占用数据的进程，然后重新启动当前应用；不删除锁文件 |
| `permission_denied` | 检查账户读写权限和安全软件限制，恢复访问后重启 |
| `disk_full` | 释放数据盘空间，为数据库及升级备份留出空间，保留原数据和备份，然后重启 |
| `storage_unavailable` | 恢复磁盘、网络目录或文件访问后重启 |
| `database_unsupported` | 核对匹配的应用版本及升级路径；也可确认备份原库后创建新数据库，并将备份交给管理员 |
| `database_corrupt` | 退出并保留整个数据目录，请维护者确认备份与恢复方案 |
| `backup_failed` | 检查存储空间、权限及连接，不跳过备份；重复失败时提供日志 |
| `migration_failed` | 保留数据与升级前备份，请维护者依据启动日志和应用版本确认修复方案 |
| `unknown` | 重新启动一次，仍失败则提供日志、版本及停止阶段 |

精确的存储错误优先于备份／迁移阶段提示。阶段只能说明失败发生的位置，
不能单凭阶段推断权限不足或数据不兼容。

启动失败不会显示仅能重读页面的“重试打开”。初始化不会因页面重读而重跑，
可自行排除的问题明确要求处理后退出并重启应用。普通页面读取失败仍保留局部重试。

## 兼容性与数据边界

启动进度 DTO 随桌面前后端一同发布，保留 schema_version=1，已有字段及错误码
desktop_startup_failed 不变；非失败状态不输出 failure_code，前端仍接受不含可选字段的已有进度。
仅当后端确认 database_unsupported 且具备恢复服务时输出 recovery_available。
新增的 BackupAndCreateDatabase / OpenDatabaseRecoveryDirectory 是随桌面一起发布的内部绑定，
不接受前端提供文件路径，不修改公开 CLI 或独立 runner 协议，也没有弃用契约或移除期限。
支持的历史数据升级范围及降级限制继续遵循 [兼容性政策](../compatibility-policy.md)。
提示中的备份恢复必须先确认匹配版本，且可能丢失备份后的记录。

## 用户确认后的备份与新库

“备份并创建新数据库”仅在数据库不兼容时显示。确认框说明新库不会带入原库的
历史记录、任务和数据库配置，要求先停止其他使用原库的工具，并提示可以将备份交给可信任的管理员。
本功能不发送文件，不修复或迁移旧库，也不清除原始库、WAL、SHM 或回滚日志。

后端重新取得桌面执行器的全生命周期锁，并再次校验实际来源仍是不兼容格式。
使用 SQLite 在线备份 API 读取固定快照，将 WAL 中尚未 checkpoint 的记录合并进
独立的 original.sqlite。通过 quick_check 校验通用 SQLite 完整性，并将实际落盘内容的
SHA-256、字节数、来源相对路径及当前应用版本记录在 backup.json（schema_version=1）。
不要求管理员备份通过当前业务 schema 校验，也不重算历史报告或结论。

创建新的独立 database-workspace-* 目录，通过现有迁移实现初始化到当前数据库版本，
验证完成后才原子发布 database-selection.json（schema_version=1）。备份目录及新库目录
分别完成持久化确认；Windows 沿用已验证迁移备份的 write-through 目录发布，目录名附加 -verified。
选择记录仅允许生成的子目录名，不接受绝对路径、上级路径、未知字段、重复字段或较新版本。
没有选择记录时沿用已发布的默认数据库路径；选择记录损坏或其数据库缺失时停止启动，不回退或静默新建。

原库保留在原命名空间；其他未知客户端不会因文件替换而丢失正在使用的数据库。
备份是一致性快照，备份后其他工具对原库的写入不会同步到新工作区。
恢复持有的执行器锁直接移交新初始化过程，只有新工作区关闭或初始化失败时才释放。
完成页提供“进入新工作区”和“打开备份文件夹”；若新库已准备但后续服务启动失败，明确引导查看新错误。

备份、建库或目录发布失败不切换工作区，已产生的诊断文件保留。切换前中断仅留下未使用的独立目录。
原子选择记录发布后即使目录同步返回错误，也保留原库和完整备份，停止重复恢复并要求退出重开确认状态。
重开只读取完整的选择记录及已校验的新库，不重复创建数据库或覆盖备份。

该选择记录是新增的持久化边界，不修改现有数据库 schema 或已发布迁移。旧二进制不识别该记录时，
仍打开原默认数据库，不会读取新工作区；这不代表能回滚新工作区中创建的记录。管理员恢复应保留完整目录、
选择记录和备份，先在副本中使用理解原数据格式的匹配版本验证。本功能不提供自动回迁或两个工作区的合并。

## 验证记录

- `GOMAXPROCS=2 go test -p 1 ./apps/desktop/...`、`go vet -p 1 ./apps/desktop/... ./internal/persistence/sqlite` 和桌面 Go 编译通过。
- 前端完整测试通过：69 个文件、1030 项；使用 1 个 worker、15 秒单项超时，设置 RAYON_NUM_THREADS=2、UV_THREADPOOL_SIZE=2 和 768 MiB Node 堆上限，降低本机资源压力。lint 只有既有的 entry-case-table.tsx effect 警告，类型检查与生产构建通过。
- Go 测试使用真实占用锁、不支持格式和损坏数据库校验分类，并检查被拒绝数据库的原始字节不变；另覆盖 SQLite 磁盘已满、Windows 磁盘错误、敏感原因不进入 DTO、正常校验与历史升级校验的区别。
- 真实临时 SQLite 测试覆盖：WAL 未合并记录及并发事务的一致性备份、备份单文件交付、哈希及字节数、取消及重复请求、执行器锁移交、新库版本与重开、各阶段失败不切换、发布后错误的重开恢复，以及无效／较新选择记录的无修改拒绝。
- 固定数据的浏览器预览检查 960×640、1024×768、1440×900，无水平溢出，提示及操作完整可见；检查中英文及 light/dark/system 主题，实际点击取消、确认、进入工作区、模拟打开备份文件夹，并验证控制台无错误或警告。
- 浏览器预览不代表原生窗口验收；备份与新库切换使用临时数据库自动化验证，本次未操作真实用户数据库，也未通过原生窗口执行恢复。
